the client-model question: agent = OAuth client vs agent = grant subject

The most contentious design question in draft-carleton-wag: does each agent instance get its own client_id and authenticate in the client-auth slot (left column, agent = client), or does the agent stay the subject of the platform-signed authorization grant with the client role left to the platform (right column, agent = subject, the current draft)? Three scenarios, worked both ways. Companion: request shapes. Status and full arguments: decision-log O4 in the repo.

The crux: Both sides agree the state that actually scales per agent (grants, jti replay, audit) grows identically under either design; the irreducible choice is which set of inventions the draft signs up for, because neither exists fully today. Agent==client inherits deployed, client_id-keyed management machinery but must invent per-instance client identity: extending the adopted family-granularity stack (CIMD/ATTEST/SPIFFE) to instance cardinality, with per-agent client_ids, family-vs-instance consent semantics, refresh custody for ephemeral instances, and IdPs that resolve per-agent identifiers -- invent new things for client management. Agent==subject inherits the registered delegation grammar (sub, act, actor_token) but must invent the management and binding plane on (iss, sub): per-agent quotas, kill switches, token listing, the consent-binding rule, and the act-in-ID-JAG composition, none of which any deployed AS enforces -- invent new things for representing delegations. There is no third stack; the tiebreakers are the adoption floor (jwt-bearer everywhere vs ATTEST/CIMD nearly nowhere) and which primary key -- client_id or (iss, sub) -- the ecosystem's per-agent state should accrete under.

what the draft owes regardless of the outcome

  • The IDJAG pointer is a live internal inconsistency: the draft's Scope section points on-behalf-of at IDJAG while D4 permits fully unauthenticated token requests, and IDJAG s4.4.1 has nothing to match on an unauthenticated request. The draft owes one normative sentence: in the IDJAG/Enterprise-IdP composition the Platform MUST authenticate as an OAuth client (D4's own reserved composition), and the agent's identity travels as act (via actor_token at the exchange). The advocate correctly caught an unclosed loop the current text leaves dangling.
  • Per-agent user consent has no enforcement rule in WAG today. The wire form exists (RFC 9396 authorization_details naming the agent; grant recorded against (user, tenancy client, agent (iss,sub))), but the binding rule — 'this grant is redeemable only alongside a fresh assertion whose sub matches the consented agent' — is unwritten profile text, and no off-the-shelf AS enforces it. Until that rule is drafted, 'grant MY email to THAT agent' is expressible but not enforceable under agent-as-subject, and the author's convenience scenario should be promoted from framing-note to a named Open Issue.
  • (iss, sub)-keyed management machinery is new build. Per-agent quotas, kill switches, token listing, and grant dashboards keyed on the agent identifier do not exist in any deployed AS, and the draft currently implies zero cost beyond the token endpoint. Honest text: adopting ASes that want per-agent operational controls build them against (iss, sub); the draft should also add at least a SHOULD for client authentication in production deployments, since an unauthenticated floor leaves the AS with no caller identity to throttle or kill — exactly the case O1's refinement already flags as load-bearing.
  • Token-shape ambiguity cuts against WAG too: RS code that assumes sub is always a human will misclassify WAG's self-access tokens (sub = agent identifier). The draft should adopt a disambiguator — a sub_profile-style claim as in McGuinness ai-agent-instance s8, or normative reliance on the URI-form identifier's authority component — rather than leaving RSes to guess. The advocate's two-shapes critique applies to their design AND to the ecosystem-converged sub/act.sub split WAG should adopt for OBO; WAG owes its half of the answer.
  • The Relationship-to-WIMSE/SPIFFE section (O3) is still a TODO, and until it exists the draft recommends WIMSE identifiers while declining SPIFFE-style client authentication without stating why. The slot argument (subject-granularity instance identity vs family-granularity client identity) is sound but currently lives in a notes file, not the draft; the advocate is right that a security reviewer will press exactly here.
  • The advocate's adoption-floor concession deserves being banked, not gloated over: their weakest_points #1 grants that D3's adoption argument survives ('WAG as drafted is a config change at the token endpoint... this trades away time-to-first-deployment'). The debate is genuinely between shipping into the deployed ecosystem now versus building for a paper end state; the draft should say it is consciously choosing the former and name the migration path (hybrid options) so the choice reads as staged, not blinkered.
